### 소프트웨어 프로세스

- 소프트웨어 프로세스
    - 체계적인 방법/접근법
    - 제품을 만드는 데 필요한 활동들의 집합(순서)
    - <u>핵심 활동</u>
        1. ==SW ====<u>명세화</u>==
        2. ==SW ====<u>개발</u>==
        3. ==SW ====<u>검증</u>==
        4. ==SW ====<u>진화</u>==
    - 보편적이지 않음
    - 설명에 중요한 것
        - 누가, 무엇이, 순서에 영향을 미치는 조건
- 소프트웨어 프로세스 모델
> 소프트웨어 프로세스를 단순하게 나타낸 것
> - SDLC, 소프트웨어 개발 생명 주기

    - 일반적인 프로세스 모델 (프로세스 패러다임)
        - ==폭포수 모델==
            - 대규모 군사 시스템 공학의 프로세스 모델에서부터 나옴
            - 전형적인 계획 기반 프로세스
            - 각 활동의 단계 명확히 분리
                1. 요구사항 <u>분석</u> 및 정의
                    - 사용자와 협의, 시스템의 서비스, 제약조건, 목표 설정
                    - 시스템 명세로 사용
                2. 소프트웨어 <u>설계 및 </u>구현
                    - 설계 프로세스를 추상화 시킨 모델
                    - 다른 소프트웨어와 사용작용함
                3. <u>단위</u> 테스팅
                4. <u>통합</u> 및 시스템 테스팅
                5. 유지 보수
            - 한계점
                - 보수적, 유연하지 못함
            - 주요 대상
                - 임베디드 시스템
                - 필수 시스템
                - 대규모 시스템
        - ==점진적 개발==
            - 초기 버전 구현 → 피드백, 개선 → V.UP → 반복…
            - 각 단계 오가며 수행
            - 장
                - 비용 절감
                - 빠른 피드백 및 사용자에게 응답 가능
            - 단
                - 비가시적
                - V.UP 시마다 잦은 코드 변경 → 시스템 구조 나빠짐
        - ==통합 및 구성==
            - 현실적으로, 하나의 모델을 기준으로 <u>기성</u> 모델들의 특성을 가져와서 개발에 활용함
            - 기성 시스템 이용
            - 웹서비스
- 프로세스 활동
> 현실 세계의 소프트웨어 프로세스

    - 과정
        1. ==명세==(Specification) — 필요한 서비스, 제약 조건
            - 시스템에 필요한 서비스 이해/정의
            - 개발 및 운영에 대한 제약 파악
            - 요구 공학이라고도 함
                - 요구사항 도출 및 분석
                - 요구사항 명세화
                - 요구사항 검증
            - <u>실수 →  무조건 오류</u>로 이어짐
        2. ==설계 및 구현==
            1. 설계
            2. 구현(프로그래밍)
        3. ==테스트==(Testing)
            3. 단계
                1. 컴포넌트 테스팅
                2. 시스템 테스팅
                3. 사용자 테스팅
    - 용어
        - 확인(Validation) — 방법적으로 맞는지
        - 검증(Verification) — 실제 사용을 고려 시 맞는지
- 소프트웨어 변경
    - <u>프로토타이핑</u>; 변경 예측
        - 요구공항 프로세스에서의 역할
        - 실제 프로세스에서의 역할
        - 프로토타입 개발 프로세스 모델
            - 목표 설정
            - 기능 정의
            - 평가
        - 문제점
    - <u>점진적 인도</u>; 변경 허용
        - 개발된 증분(increments)을 고객에게 전달/배포
- 프로세스 개선
    - 산업계의 끊임없는 요구 (더 저렴하고 빠르게)
    - 기존 프로세스 이해, 프로세스 변경 → 제품 품질 향상, 개발 시간 단축
    - 방식
        - ==프로세스 성숙도== 접근법
> 성숙한 프로세스

            1. 초기 — <u>개인</u>
            2. 관리 — <u>관리</u>
            3. 정의 — <u>조직</u> 차원
            4. 정량적 관리 — <u>통계</u>, 측정
            5. 최적화 — <u>피드백</u>
        - ==애자일== 접근법
> 사람, 소통, 피드백
- [ ] ==해야 할 것 → 각 시스템== 별, 가시화(그래픽으로 표현)

### 시스템 모델링

- 시스템 모델링
    - 개념
        - 실제 세계의 시스템을 추상화하여 표현하는 프로세스
        - 시스템의 특정 측면을 단순화하고 명확하게 보여줌
    - 중요성
        - 이해관계자 소통
        - 설계 명확화
        - 오류 감소
        - 문서화
        - 복잡성 관리
        - 재사용성 증대
    - 시스템 모델에 대한 이해
        - 이해를 위해 의도적으로 누락한 부분 존재(대채적 표현 X, 추상 모델 O)
![[image 74.png]]
- 개발 생명 주기에서의 시스템 모델링
    - 요구사항 분석 단계
    - 설계 단계
    - 구현 단계
    - 테스트 단계
    - 유지보수 단계
- 좋은 모델의 속성
    - 정확성: 실제 시스템의 중요한 측면 반영
    - 명확성: 표준 표기법
    - 간결성: 필요한 정보만 포함
    - 일관성: 모든 요소와 다이어그램의 일관성 유지
    - 현실 반영
- 다양한 모델
    1. 외부 관점: 컨텍스트 모델(Context Model)
        - 개념
            - 시스템 운영 상황 설명
            - 경계가 모호할 수 있음
            - 비기술적 요소(사회적/조직적 고려사항)에 의해 결정될 수 있음
            - 비즈니스 프로세스 모델
            - 액티비티 다이어그램으로 표현
                - 맥락, 절차의 동적 표현
    2. 상호작용 관점: 상호작용 모델(Interaction Model)
        - 개념
            - 시스템에서의 다양한 상호 작용
                1. 사용자 <—> 시스템
                2. 시스템 컴포넌트들 간
                3. 시스템 <—> 외부 시스템
        - 역할
            1. -
            2. -
            3. -
        - [==유스케이스(Use Case) 모델링==](/319f9f43a085808896d3cad95b50c75e#32ef9f43a0858056b407de7a869cd8c9)
            - 사용자가 시스템에 기대하는 행위 간략히 기술
            - 외부 요소와의 상호작용 중심
        - [==시퀀스 다이어그램 모델링==](/319f9f43a085808896d3cad95b50c75e#33cf9f43a08580729fd1fc3f4ef1a461)
            - 시퀀스 다이어그램
            - 기본적 표기법
            - 설명
    3. 구조적 관점: 구조 모델(Structural Model)
        - 개념
            - 컴포넌트와의 관계 시각화
                - 시스템 정적 구성 —> 클래스 다이어그램
                - 실행 중 시스템 내부 구성 변화(동적) —> 객체 다이어그램
        - [==클래스 다이어그램==](/319f9f43a085808896d3cad95b50c75e#33af9f43a0858021b965f4844709ab98)
            - 수준
                - 개략 수준
                - 중간 수준
                - 상세 수준
            - 집합
            - 합성
    4. 행위적 관점: 동작 모델(Behavioral Model)
        - 시스템 실행 시의 동적인 행위에 대한 모델
        - 데이터-주도 모델링

- 객체 다이어그램(Object Diagram)
> 다양한 개체(객체)로 구성

    - 구성 요소
        - 클래스의 이름
        - <u>속성</u>(Attribute; 구조적 특성) — 구체적인 값 할당
        - <u>오퍼레이션</u>(Operation) — 묘사되지 않음
    - 표현(표기법)
        - 직사각형(세 칸)
            - 첫번째 칸 — `객체이름 : 클래스`
            - 두번째 칸 — `속성이름 : 타입 (= 기본값) {추가적인 특성}`
                1. 추가 특성 — `{추가특성}`
                2. 유도 속성 — `/속성이름`
                    - 다른 이름으로부터 유도됨
                3. <u>다중성</u> — `[속성개수]`
                    1. 속성을 가질 수 있는 값의 개수추
                4. 클래스 변수
            - 세번째 칸 — `오퍼레이션` 
                1. 가시성 표시
        - 연관(Associations)
            - 클래스의 인스턴드들 간 <u>가능한 관계</u>(Link)
            - 값 참조 방향성(Navigability) 표현 — `<— / —>`
            - 연결의 다중성 표현 — 연관될 수 있는 객체의 수 `..*`
            - 연관 표현
                - 배타적 연관
                - 집합 연관
                - 공유 집합 연관
            - 종류
                - 단일 연관(Binary Associations)
            - 소속감(약한, 강한) 표현
        - 상속(Inheritance)
        - 일반화(Generalizaations)
        - 포함되지 않는 정보
            - 간소화; 존재하지 않는 정보는 아님
    - 핵심 개념
        - 클래스
        - 인스턴스 — 클래스의 구체적인 형태

### 소프트웨어 테스팅

- 정의
    - <u>명시된 요구</u>를 잘 만족하는지 확인
    - <u>예상된 결과</u>와 <u>실제 결과</u> 비교
    - 결함이 있음을 볼 수 있음 (<u>결함이 없음을 증명할 수 없음</u>)
- 목적
    - 작은 의미
        - 존재하지만 드러나지 않고 숨어 있는 오류 발견
    - 큰 의미
        - 고객의 요구 만족시키는지 확인
        - 사용하기 충분한 소프트웨어임을 보여주기  —> 개발자, 고객
> [!tip] 💡

    - 현실적인 어려움
